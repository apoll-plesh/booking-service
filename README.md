# Сервис бронирования переговорных «Бронь без конфликтов»

Учебный проект по дисциплине «Разработка веб-сервиса бронирования ресурсов».

## Назначение

Веб-сервис для бронирования **переговорных комнат** образовательной организации. Каждая переговорная — отдельный ресурс со своей карточкой. Пользователь выбирает свободное время, создаёт бронирование и управляет своими записями. Администратор управляет переговорными и видит все брони.

**Главное требование:** одна переговорная не может быть забронирована на пересекающиеся интервалы времени — даже при одновременных запросах от разных пользователей.

## Вид ресурса

**Переговорные комнаты.** У каждой — название, описание, местоположение (корпус/этаж/номер) и признак активности.

## Роли пользователей

| Роль | Что может |
|---|---|
| **Пользователь** | Войти, просмотреть каталог, увидеть занятые интервалы, создать бронь для себя, посмотреть свои брони, отменить свою будущую бронь |
| **Администратор** | Всё, что пользователь, плюс: видеть все брони и их владельцев, отменять любую будущую бронь с причиной, создавать/редактировать/отключать переговорные, просматривать аудит действий |

## Правила времени

- Переговорные доступны **ежедневно с 08:00 до 22:00 по московскому времени (МСК)**.
- **Шаг выбора времени** — 30 минут.
- **Продолжительность брони** — от 30 минут до 4 часов.
- Бронь **целиком помещается в один рабочий день**.
- **Окончание позже начала**.
- **Начало** не находится в прошлом и не позднее чем **через 30 суток** от текущего момента.
- Все проверки выполняются **по серверному времени**, а не по времени браузера.
- API принимает дату **со смещением часового пояса** (ISO 8601, например `2026-10-20T10:00:00+03:00`).
- База данных хранит **однозначный момент в UTC**.
- Интерфейс **явно указывает московское время**.

## Правило пересечения интервалов

Интервал имеет вид **[начало, окончание)** — момент окончания свободен.

Конфликт существует, когда:

> начало новой записи **раньше** окончания существующей **И** окончание новой записи **позже** начала существующей.

| Существующая запись | Новая запись | Результат |
|---|---|---|
| 10:00–11:00 | 09:00–10:00 | Разрешено (соседние) |
| 10:00–11:00 | 11:00–12:00 | Разрешено (соседние) |
| 10:00–11:00 | 10:00–11:00 | Конфликт (полное совпадение) |
| 10:00–11:00 | 09:30–10:30 | Конфликт (пересечение в начале) |
| 10:00–11:00 | 10:30–11:30 | Конфликт (пересечение в конце) |
| 10:00–11:00 | 09:00–12:00 | Конфликт (новая шире) |

**Важно:**
- Проверка относится **к одному ресурсу** и **только к активным записям**.
- **Отменённые записи не занимают время** — освободившийся интервал можно забронировать снова.
- **Разные переговорные** могут бронироваться одновременно.

## Правила отмены

- **Владелец** может отменить **свою будущую** бронь (до её начала).
- **Администратор** может отменить **любую будущую** бронь **с обязательной причиной**.
- **Начавшиеся и завершённые** брони отменять нельзя.
- **Повторная отмена** не создаёт нового изменения состояния (идемпотентна).
- При отмене **сохраняются**: сама запись, кто отменил, время действия, причина.
- Отменённая запись **освобождает время** — на этот интервал можно создать новую бронь.

## Правила доступа и безопасности

- **Владелец новой записи** определяется **сервером по проверенному JWT**, а не по данным от клиента.
- Если клиент пришлёт чужой `userId` или роль — сервер **игнорирует** это и использует данные из токена.
- При чтении и отмене сервер проверяет **владельца записи** либо **административные полномочия**.
- **Чужая запись** для обычного пользователя возвращается как **404 Not Found** (не 403) — чтобы не раскрывать её существование.
- **Административные маршруты** при обращении обычного пользователя возвращают **403 Forbidden**.
- Защита работает **при прямом запросе** (curl, Postman), даже если кнопка в интерфейсе скрыта.

## Отключение ресурса

- **Отключённый ресурс** недоступен для **новых** бронирований.
- **Существующие** записи сохраняются.
- Администратор при необходимости отменяет будущие записи вручную (с причиной).
- **Физическое удаление** ресурсов и бронирований через интерфейс **не реализуется**.


## Основной сценарий

1. Пользователь открывает страницу входа.
2. Вводит логин и пароль.
3. Сервер проверяет учётные данные, выдаёт **JWT**.
4. Клиент сохраняет токен и переходит в **каталог переговорных**.
5. Пользователь ищет переговорную по названию или фильтрует по местоположению.
6. Открывает **карточку** переговорной: описание, выбор даты, список занятых интервалов (без ФИО и целей других пользователей).
7. Выбирает **свободное время**: дату, начало, окончание.
8. Заполняет **цель брони** (5–300 символов).
9. Нажимает «Забронировать». Клиент отправляет `POST /api/bookings` с **Idempotency-Key** (одноразовый ключ).
10. Сервер:
    - проверяет JWT;
    - валидирует формат, ресурс, диапазон времени;
    - проверяет конфликт с активными записями;
    - создаёт запись в БД;
    - сохраняет ключ идемпотентности;
    - пишет событие аудита.
11. Клиент получает ответ с **номером брони** и показывает подтверждение.
12. Пользователь переходит в раздел **«Мои бронирования»** и видит свою запись.

## Альтернативные сценарии

### A1. Ресурс отключён
Пользователь пытается забронировать переговорную, у которой `isActive = false`.
**Ожидание:** сервер возвращает `400 Bad Request` с сообщением «Ресурс недоступен для бронирования». Запись не создаётся.

### A2. Время занял другой пользователь
Пока пользователь заполнял форму, кто-то успел забронировать этот же интервал.
**Ожидание:** сервер возвращает `409 Conflict` с сообщением «Ресурс уже занят в выбранное время». Вторая активная запись **не создаётся**. В интерфейсе показывается ошибка, пользователь может выбрать другое время.

### A3. Неверные даты
Например: окончание раньше начала, длительность <30 минут или >4 часов, выход за пределы 08:00–22:00 МСК, шаг не кратен 30 минутам, начало в прошлом, начало позже чем через 30 суток.
**Ожидание:** сервер возвращает `400 Bad Request` с описанием конкретной ошибки у поля. Запись не создаётся.

### A4. Истёк или отсутствует JWT
Клиент отправляет запрос без токена или с просроченным.
**Ожидание:** сервер возвращает `401 Unauthorized`. Клиент предлагает **повторный вход**. Данные формы **не теряются**.

### A5. Ответ потерян (сетевой сбой)
Пользователь нажимает «Забронировать», сервер **создаёт запись**, но ответ до клиента не дошёл (например, пропал интернет после отправки).
**Ожидание:**
- клиент сохраняет введённые данные;
- при повторе отправляется **тот же** `Idempotency-Key` и **те же** данные;
- сервер возвращает **ту же самую бронь** (тот же ID), без новой вставки;
- в БД остаётся **одна** запись.

### A6. Кнопка нажата повторно
Пользователь дважды кликнул «Забронировать» до ответа сервера.
**Ожидание:** благодаря блокировке кнопки на клиенте и `Idempotency-Key` на сервере создаётся **только одна** бронь. Второй запрос возвращает тот же результат.

### A7. Попытка доступа к чужой записи
Пользователь подставляет в URL ID чужой брони.
**Ожидание:** сервер возвращает `404 Not Found`. Данные чужой записи **не раскрываются**.
**Администратор** в этом случае видит запись (у него есть права).

### A8. Обычный пользователь на админ-маршруте
Пользователь напрямую вызывает `/api/admin/...`.
**Ожидание:** сервер возвращает `403 Forbidden`. Функция не выполняется.

## Схема данных (план)

Пять основных сущностей:

| Сущность | Что хранит |
|---|---|
| **users** | ID, имя, логин, хеш пароля, роль (`user` / `admin`) |
| **resources** | ID, название, описание, местоположение, признак активности |
| **bookings** | ID, ресурс, владелец, начало, окончание, цель, статус (`active` / `cancelled`), время создания, сведения об отмене |
| **idempotency_keys** | Пользователь, ключ, отпечаток запроса, ссылка на созданную бронь (уникальность: пользователь + ключ) |
| **audit_events** | Время, исполнитель, действие, объект, результат, ID запроса |

Полная SQL-схема с ограничениями и индексами — в `migrations/001_init.sql` (будет на Этапе 2).

## Описание API (план)

| Метод и маршрут | Назначение | Доступ |
|---|---|---|
| `GET /api/resources` | Каталог активных ресурсов с поиском и фильтром | Авторизованные |
| `GET /api/resources/{id}` | Карточка ресурса | Авторизованные |
| `GET /api/resources/{id}/availability` | Занятые интервалы выбранной даты | Авторизованные |
| `POST /api/bookings` | Создание брони для текущего пользователя | Пользователь, админ |
| `GET /api/bookings/my` | Собственные записи | Пользователь, админ |
| `GET /api/bookings/{id}` | Просмотр доступной записи | Владелец или админ |
| `POST /api/bookings/{id}/cancel` | Отмена с проверкой прав и времени | Владелец или админ |
| `GET /api/admin/bookings` | Все записи с фильтрами | Только админ |
| `POST /api/admin/resources` | Создание ресурса | Только админ |
| `PATCH /api/admin/resources/{id}` | Изменение и отключение ресурса | Только админ |
| `GET /api/admin/audit` | Просмотр аудита | Только админ |
| `GET /health/live` | Проверка «процесс жив» | Публичный |
| `GET /health/ready` | Проверка «сервис готов» (БД) | Публичный |

Полное описание с параметрами и кодами ответов — в `docs/api.md` (будет по мере реализации).

## Коды ошибок

| Код | Когда |
|---|---|
| `400` | Неверные поля, невалидный диапазон времени |
| `401` | Нет JWT или он истёк |
| `403` | Попытка использовать админ-функцию без прав |
| `404` | Запись не найдена или недоступна |
| `409` | Конфликт времени / повтор ключа с другими данными |
| `500` | Непредвиденная ошибка (без внутренних деталей) |

Формат ответа об ошибке:

```json
{
  "code": "BOOKING_CONFLICT",
  "message": "Ресурс уже занят в выбранное время",
  "traceId": "a1b2c3d4"
}


## CI/CD

При каждом пуше в `master` GitHub Actions выполняет:
1. `npm ci` — чистая установка по `package-lock.json`.
2. `npm run lint` — проверка кода ESLint (ошибки → CI красный, публикация блокируется).
3. Сборка артефакта `booking-service-<sha>.tar.gz` с исходниками.
4. Загрузка артефакта в GitHub Actions (хранится 30 дней).

Секреты (например, `DB_PASSWORD`) хранятся в **Settings → Secrets → Actions** и не попадают в репозиторий.

### Health-проверки

- `GET /health/live` — процесс жив (для мониторинга).
- `GET /health/ready` — сервис готов (проверяет подключение к БД; при недоступности БД — 503).

### Применение миграций при деплое

Перед первым запуском (и при каждом обновлении схемы): npm run migrate

Скрипт идемпотентен: повторный запуск пропускает уже применённые миграции (см. таблицу `_migrations`).


## Резервное копирование и восстановление

**Создание резервной копии:**
pg_dump -U postgres -d brony -F c -f brony_backup.dump


**Восстановление в отдельную БД:**
createdb -U postgres brony_test
pg_restore -U postgres -d brony_test brony_backup.dump

**Проверено:** восстановленная БД содержит те же таблицы, данные, ограничения (включая `EXCLUDE`). Контрольная бронь `id=N_control` на месте. Приложение работает с восстановленной БД.

**Требования:** PostgreSQL 18, права суперпользователя (или владельца БД), утилиты `pg_dump`, `pg_restore`, `createdb`, `dropdb` в `PATH`.

**Хранение копии:** локальная папка `backup/` (в `.gitignore`), вне репозитория. В реальной эксплуатации — отдельное защищённое хранилище.
