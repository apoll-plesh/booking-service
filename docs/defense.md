# Подготовка к защите

## Вопрос 1. Почему JWT недостаточно для доступа к записи?

JWT подтверждает **кто** вы (аутентификация), но не даёт прав на **конкретную** запись.

Пример: пользователь `user1` получает валидный JWT и с ним обращается к `POST /api/bookings/42/cancel`. Если сервер проверяет только JWT — он пропустит запрос, и `user1` отменит чужую бронь. JWT валиден, но прав на эту запись у него нет.

**Что делаем:**
1. JWT проверяется middleware `verifyToken` (кто вы).
2. Затем в контроллере `cancel` загружаем бронь из БД и проверяем: `booking.owner_id === req.user.id` **или** `req.user.role === 'admin'`.
3. Чужая запись → **404** (не 403, чтобы не раскрывать существование).

**Вывод:** JWT — необходимый, но недостаточный уровень. Права на объект проверяются **на сервере**, по данным из БД, а не по данным от клиента.

## Вопрос 2. Почему проверка перед вставкой не исключает гонку?

Классическая ошибка: «проверить, что время свободно → вставить запись». Два запроса могут выполнить проверку **одновременно**, оба увидят «свободно», оба вставят — конфликт.

```
Запрос A: SELECT ... (свободно) → INSERT ✓
Запрос B: SELECT ... (свободно) → INSERT ✓   ← оба прошли!
```

**Наше решение:** проверку делает **сама БД** через `EXCLUDE`-ограничение:

```sql
EXCLUDE USING gist (
  resource_id WITH =,
  tstzrange(start_time, end_time, '[)') WITH &&
) WHERE (status = 'active')
```

При `INSERT` PostgreSQL **атомарно** проверяет пересечение с существующими активными записями. Если есть конфликт — возвращает ошибку `23P01` (exclusion_violation), и транзакция откатывается. Даже при 100 одновременных запросах вставится ровно **одна** запись.

**Ключевой момент:** проверка встроена в БД, а не в код приложения. Работает на любом числе экземпляров сервера.

## Вопрос 3. Что произойдёт при потере ответа?

Пользователь нажал «Забронировать», сервер **создал** запись, но ответ до клиента не дошёл (обрыв сети). Клиент не знает, создалась ли бронь, и при повторе может создать **дубликат**.

**Наше решение — идемпотентность через `Idempotency-Key`:**
1. Клиент генерирует UUID **до первой отправки** и хранит его.
2. При повторе отправляет **тот же ключ** и **те же данные**.
3. Сервер в **одной транзакции**:
   - ищет ключ в `idempotency_keys` для этого пользователя;
   - если найден и отпечаток данных совпадает — возвращает **исходную бронь** (без новой вставки);
   - если найден и данные **другие** — возвращает **409**;
   - если не найден — создаёт бронь и **сохраняет ключ**.
4. Уникальность `(user_id, key)` в БД гарантирует, что даже два одновременных запроса с одним ключом дадут **один** результат (второй получит 409 и повторит, увидев ключ).

**Вывод:** при потере ответа клиент повторяет запрос с тем же ключом — сервер вернёт **ту же бронь**, дубликата не будет.

## Вопрос 4. Чем ключ повтора отличается от проверки пересечения?

Это **два независимых механизма** для разных проблем:

| | Проверка пересечения (`EXCLUDE`) | Ключ повтора (`Idempotency-Key`) |
|---|---|---|
| **Проблема** | Два **разных** пользователя бронируют **один** интервал | **Один** пользователь повторяет **свой** запрос |
| **Инструмент** | `EXCLUDE USING gist` в БД | `idempotency_keys` + уникальность `(user_id, key)` |
| **Результат** | Второй запрос → **409 BOOKING_CONFLICT** | Повтор с тем же ключом → **201 с исходным id** |
| **Когда срабатывает** | Всегда, при любом создании | Только если клиент прислал ключ, который уже был |

**Ключ повтора не заменяет проверку пересечения.** Если убрать `EXCLUDE`, два пользователя с разными ключами создадут дубль. Если убрать `Idempotency-Key`, один пользователь при повторе создаст дубль.

**Нужны оба механизма.**

## Вопрос 5. Как решение работает на двух серверах?

**Проверка пересечения** — встроена в **БД**. PostgreSQL — единая точка правды. Даже если 10 экземпляров приложения одновременно вставят пересекающиеся брони, БД атомарно отвергнет все, кроме одной.

**Идемпотентность** — тоже в **БД**. `UNIQUE (user_id, key)` в `idempotency_keys`. Если два экземпляра одновременно получат запрос с одним ключом:
- первый вставит ключ;
- второй получит `unique_violation` (23505), вернёт 409, клиент повторит — увидит ключ, вернёт исходную бронь.

**Блокировки в памяти процесса — недостаточны.** Они работают только в пределах одного экземпляра. У нас ничего в памяти: все гарантии — на уровне БД.

**Итог:** решение **горизонтально масштабируется**. Можно запустить N экземпляров за балансировщиком — корректность сохранится.

## Вопрос 6. Как доказана пригодность резервной копии?

Файл бэкапа **без восстановления** — не доказательство. Мы сделали **полный цикл**:

1. Создали **контрольную бронь** (id = N_control) с известными параметрами.
2. Сделали бэкап: `pg_dump -F c -f brony_backup.dump`.
3. Создали **отдельную** БД `brony_test` (рабочую не трогали).
4. Восстановили: `pg_restore -d brony_test brony_backup.dump`.
5. Подключили тестовый экземпляр сервиса к `brony_test` (поменяли `DB_NAME` в `.env`, перезапустили).
6. Проверили:
   - вход под `user1` работает;
   - каталог ресурсов — 6 штук;
   - контрольная бронь id=N_control на месте, параметры совпадают;
   - `EXCLUDE`-ограничение восстановилось (проверили через `pg_constraint`);
   - попытка создать пересекающуюся бронь → 409 (ограничение работает).
7. Вернули `DB_NAME=brony`, удалили `brony_test`.

**Результат:** восстановленная БД **функционально эквивалентна** рабочей. Пригодность бэкапа **подтверждена работой приложения**, а не просто наличием файла.

## Краткая шпаргалка для защиты

**3 обязательных условия зачёта:**
1. Приложение запускается, создание и отмена работают.
2. Обычный пользователь не читает и не изменяет чужие бронирования.
3. Параллельные запросы не создают пересекающиеся активные записи одного ресурса.

**Порядок защиты (10–15 минут):**
1. Назначение и схема данных — 1–2 мин.
2. Создание и отмена через интерфейс — 2–3 мин.
3. Отказ при доступе к чужой записи — 1–2 мин.
4. Конкурентные запросы и объяснение защиты — 3–4 мин.
5. Повтор запроса с ключом — 1–2 мин.
6. CI/CD, журналы и результат восстановления — 2–3 мин.

**Что показать в первую очередь:**
- `docs/manual-testing.md` — 15 проверок, все пройдены.
- `scripts/concurrent-test.js` — живой запуск, один 201 + один 409.
- GitHub Actions — зелёный CI и история падения в `test-fail`.
- `pg_constraint` — ограничение `bookings_no_overlap` существует.
